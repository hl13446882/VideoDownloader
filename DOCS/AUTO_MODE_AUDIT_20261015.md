# 自动模式自治能力审计

日期：2026-10-15。对象：当前工作区代码（版本 1.1.24）。

结论：具备正常页面上的自动采集能力，尚不具备可验证的长期无人值守自治能力。这里的自治指：维持既定目标，检测停滞，有限重试或降级，恢复故障，且能准确报告未完成工作。本次只审计，未修改业务代码或再次发布。

## 已具备的能力

- 按配置时长或数量结束；0 表示不限。
- 消费正常探测流程的第一张可下载卡片，不另起探测流程。
- 跳过直播；无地址约一分钟后尝试切页。
- 等待并发名额；下载开始后延迟约三秒切页。
- 记忆上一条入队内容和最近一次入队失败，避免紧邻重复。
- 下载引擎具备部分换地址、Cookie 刷新和失败重试；部分外部媒体进程具备无进度监控。

## 发现（按优先级）

### 1. [P1] HTTP 响应体停滞可能永久占用下载名额

证据：`src/VideoDownloader.Infrastructure/Http/HttpMediaDownloader.cs:666` 使用 ResponseHeadersRead；`:912–918` 随后用任务取消令牌直接读取响应体，没有为读取设置独立的无进度超时。并行读取路径 `:611–614` 同样如此。HttpClient 的请求超时不能充当 ResponseHeadersRead 返回之后的响应体读取超时。

触发：服务器已返回响应头，之后保持连接却不继续发送数据。

影响：运行任务可以一直等待读取，持有并发名额；名额全被占用时，自动模式在 `MainViewModel.cs:2578` 等待，无法继续采集。有限时长只会结束采集循环，不会取消这些独立下载任务。

建议：在现有 HTTP 下载器内增加可随字节进度重置的空闲超时，保留外部取消语义；超时必须进入现有失败、释放名额及恢复路径。不要增加第二套下载器。

### 2. [P1] 无限时长下，切页失败没有退出或恢复边界

证据：`src/VideoDownloader.UI/ViewModels/MainViewModel.cs:2238` 将不限时长设置为 DateTime.MaxValue；`:2723–2744` 的切页等待仅受会话截止时间和取消令牌控制，每两秒再次发送快捷键。没有单次切页超时、次数上限或其他恢复阶段。

触发：快捷键失效、页面没有下一条、登录/验证码覆盖页面，或内容标识始终不更新。

影响：状态可以长期显示运行，但不产生新任务。有限时长会等到整个会话结束后停止，而不是及时恢复。

建议：为切页设置独立期限和重试预算；超限后走现有页面/探测会话的受控恢复入口，恢复失败时明确终止并保留原因。不能简单把循环改成无休止刷新。

### 3. [P1] 浏览器脚本等待可能绕过会话期限和停止操作

证据：`MainViewModel.cs:2306` 调用 SendFeedNextAsync 时未传递自动模式的取消令牌。`src/VideoDownloader.Infrastructure/Browser/WebView2Host.cs:117–146` 内部等待 ExecuteScriptAsync，仅应用传入的令牌。直播检查虽然传令牌，但也没有独立超时；会话截止时间只是循环判断，没有转换成自动到期的取消令牌。

触发：WebView 渲染进程卡住，脚本调用迟迟不完成。

影响：停止自动模式、到达时长限制均不能保证及时退出当前等待；后续也无法进入故障恢复。

建议：贯通会话令牌，为浏览器调用增加操作级超时，并区分用户取消、操作超时和页面故障。

### 4. [P2] 入队后的常见失败缺少自动会话层面的补偿

证据：`MainViewModel.cs:2371–2409` 只等待任务开始，随后计数并切页；`:2708–2713` 将 Preparing、Downloading、Muxing、Completed 都视为已开始。`DownloadEngine.cs:2026–2040` 明确排除 ContextExpired、NetTimeout、IncompleteDownload 和 Http403 的定时重试。

影响：引擎内部恢复耗尽后，这些任务会保持失败；自动模式可以继续采集，但不保证本次采集目标最终完成。数量限制表示已启动/命中的任务数量，不是成功下载数量。已有完成任务也可能计数。

建议：明确采集数量与成功数量的产品语义；在现有任务状态上记录会话归属和最终结果，对可恢复失败使用有预算的现有恢复入口，并最终汇总失败。排除同 URL 盲重试本身有合理原因，不能直接删掉保护条件。

### 5. [P2] 会话隔离不足，停止/重启或切标签页可能影响另一轮任务

证据：`MainViewModel.cs:2610–2634` 的 Dispatcher 入队回调没有在入队前核对当前会话及令牌，也没有向 EnqueueAsync 传入会话取消令牌；`:2428` 的异常处理和 `:2499–2506` 的结束处理操作共享 _autoCts/IsAutoMode，没有会话身份检查。只有 finally 中做了部分令牌身份校验。

触发：旧会话仍有浏览器或入队操作在等待时，用户停止后立刻开始新会话。

影响：旧操作可能在停止后继续入队、更新新会话的指纹，或通过结束处理关闭新会话。切换标签页时，`:1068` 不绑定或暂停原自动会话；自动循环持续读取 SelectedTab，因此目标会跟随当前标签页变化。

建议：为现有循环引入不可变会话身份和启动标签页身份；所有异步回调在产生副作用之前核对身份；停止后等待或隔离旧循环。切标签页行为应明确为暂停、停止或显式转移。

### 6. [P2] 重启只能恢复部分下载，不能恢复自动采集目标

证据：自动模式启动仅保存时长和数量偏好（`MainViewModel.cs:2227`），未持久化会话是否运行、目标页面、进度或剩余预算。`DownloadEngine.cs:760–770` 启动恢复只启动并发预算以内的任务，多余任务明确保留原状态等待用户操作；对应测试也验证了这一行为。

影响：崩溃或重启后，自动采集不会续跑；大量中断任务也不会全部自行排空。这属于当前恢复策略的能力边界，不能宣称自动模式已具备重启自治。

建议：先定义恢复策略和用户期望，再在现有持久化和调度路径中保存、恢复会话。恢复队列时仍须遵守既有并发和下载恢复规则。

## 验证与限制

运行了 RecoverOnStartupConcurrencyTests 和 ProcessProgressTests，共 7 项全部通过，覆盖启动恢复预算及外部进程无进度/取消处理。这些测试通过不能证明 HTTP 响应体读取或自动模式闭环无故障。

本次未找到针对自动模式主循环、切页失败预算、停止/重启竞态和会话恢复的专门测试。未进行真实站点长时间运行、断网、验证码或渲染进程故障注入。因此，上述结果是代码审计及既有测试验证，不是长期实站自治认证。

建议修复顺序：HTTP 无进度超时 → 浏览器调用期限及取消 → 切页恢复预算 → 会话隔离 → 失败结果闭环 → 按明确策略恢复会话。完成后再进行有界故障注入和长时间运行验收。
